# Flex Node — Production SAMP/CRMP Hosting

## Это именно игровой хостинг

Пользователь не получает VDS и не должен администрировать Linux.

Он создаёт игровой сервер в панели, после чего Flex Node:

1. выделяет порт;
2. создаёт директорию сервера;
3. создаёт/запускает отдельный Docker container;
4. применяет RAM/CPU/PID limits;
5. монтирует файлы сервера;
6. сохраняет состояние в MySQL;
7. Worker следит за контейнером и поднимает его после сбоя;
8. пользователь управляет сервером через панель.

## Где это размещать

Layero/Vercel-подобный free runtime с 0.25 vCPU / 256 MB не является подходящим местом для постоянных игровых процессов SAMP/CRMP.

Используй:
- VPS;
- dedicated server;
- cloud VM;
- либо несколько Worker Nodes.

Панель/API можно размещать на Layero/Vercel-подобной платформе, если она поддерживает долгоживущий Node API и внешнюю MySQL.

Игровой Worker должен находиться на VPS с Docker, публичным IPv4 и открытым UDP диапазоном.

## Порты

Нельзя обещать буквально любой порт.

Flex Node должен выдавать свободный порт из разрешённого диапазона, например 7777–8777. Firewall/security group и провайдер должны разрешать UDP.

В production нужен allocator:
- проверить занятость;
- зарезервировать порт в БД транзакцией;
- выдать его одному серверу;
- освободить после удаления.

## 24/7

`restart=unless-stopped` и Worker reconciliation позволяют восстанавливать игровые контейнеры после crash/reboot.

Но «работает до 2038 года» программно гарантировать нельзя: зависит от VPS-провайдера, IP, диска, ОС, Docker, домена и обновлений.

Правильная production-цель — автоматическое восстановление и миграция на другую Worker Node.

## SAMP и CRMP

Flex Node должен использовать совместимые server images для конкретного runtime:
- SAMP Linux;
- CRMP Linux/совместимый runtime.

Пользователь загружает свой server package/mod и запускает его в выделенном контейнере.

Для Windows-only серверных бинарников понадобится отдельный Windows Worker или совместимый runtime; Linux Docker не делает Windows-бинарники нативно совместимыми.

## Безопасность

Перед публичным запуском обязательно:
- не давать пользователю Docker socket;
- Worker держать отдельно;
- ограничения RAM/CPU/PIDs;
- disk quotas;
- file upload limits;
- rate limits;
- проверка архивов;
- backup/snapshot;
- audit log;
- TLS;
- отдельный MySQL;
- секреты только через environment/secret manager.
